# Decisions

Append-only. A changed decision is a new entry that supersedes the old one.

## #1 — Angular with CLI defaults (2026-11-05)

Latest Angular (22) generated by the CLI: standalone, zoneless, signals, Vitest, `app` prefix, no SSR.
Why: CLI defaults are the best-supported path and the simplest to upgrade.

## #2 — npm as package manager (2026-11-05)

npm only; no Bun, Yarn or pnpm.
Why: ships with Node, so the Docker build and CI need no extra tooling.

## #3 — `"type": "module"` in `package.json` (2026-11-05)

Why: the lint tooling is TS ESM; without it Node warns on every run.

## #4 — Oxlint with lint-enforced layers, no ESLint (2026-11-05)

Oxlint is the only linter; layer boundaries are `no-restricted-imports` overrides in `.oxlintrc.json`. The anti-slop plugin from the init guide is not vendored yet: installing it from an external source was blocked in the setup environment.
Why: fast, near-zero config, and architecture rules fail the lint instead of relying on review.

## #5 — Angular Aria + CDK as the only UI libraries (2026-11-05)

No Material, PrimeNG, Tailwind or other UI kits; installed when the first primitive needs them.
Why: behavior and accessibility from Angular, look fully ours.

## #6 — Plain CSS with cascade layers (2026-11-05)

`reset, tokens, base, ui, patterns, utilities`, one global entry in `src/styles.css`.
Why: predictable precedence without `!important` or a CSS framework.

## #7 — Layer folders: app root, `core/`, `shared/`, `features/` (2026-11-05)

Why: clear import direction, no type folders, features stay independent.

## #8 — Data via `httpResource` and relative `/api` paths (2026-11-05)

Reads with `httpResource`, writes with `firstValueFrom`, dev proxy via `proxy.conf.json`.
Why: signal-native data flow and the same URLs in dev, Docker and production.

## #9 — Signal Forms only (2026-11-05)

Why: one forms model that fits signals; no reactive/template forms mix.

## #10 — Serbian UI, English code (2026-11-05)

UI text in Serbian (Latin, `sr-Latn` locale); code, comments and commits in English.
Why: users are Serbian-speaking; code stays readable for any developer and tool.

## #11 — Short `CLAUDE.md`, rules in `docs/` (2026-11-05)

Why: `CLAUDE.md` loads on every task; detailed rules are read only when relevant.

## #12 — Docker image: Node build + nginx (2026-11-05)

Multi-stage `Dockerfile`, static files served by nginx with SPA fallback.
Why: the web app is dockerized like the backend; nginx is small and standard for static SPAs.

## #13 — Built-in Angular i18n, sr-Latn + en (2026-11-05)

`@angular/localize` with explicit `@@` keys for all UI text; source `sr-Latn`, translation `en`; one build per locale under `/sr-Latn/` and `/en/`. Supersedes the manual `LOCALE_ID` from #10.
Why: first-party, no runtime library, no translation lookup cost; switching language is a navigation between locale paths, which also keeps URLs shareable and indexable.

## #14 — Web app lives in `web/` (2026-11-05)

Moved from `apps/web/` to match the monorepo layout in the root README (`backend/`, `web/`, `ios/`).
Why: one convention for the whole repo.

## #15 — Serbian at the site root, English under `/en/` (2026-11-05)

Supersedes the `/sr-Latn/` path from #13: the source locale builds to the root.
Why: the guest URL stays `{tenant}.menuly.app/{venue}` as the MVP spec says; the cost is that `en` can't be a venue slug.

## #16 — Hand-written auth on `HttpClient` + signals (2026-11-05)

`AuthStore`, a functional interceptor and functional guards in `core/auth/`; tokens in `localStorage`; no auth library.
Why: the API's auth is plain JWT + rotating refresh token in the request body, which needs little code; a library would add more surface than it saves. Revisit if the API moves the refresh token to an httpOnly cookie.

## #17 — One app, two hosts (2026-11-05)

The tenant subdomain serves only the public menu; the app host serves auth and admin. The host is read once (`APP_HOST`) and routes pick a tree with `canMatch`.
Why: one build and deploy for both, and the guest menu never loads admin code (lazy).

## #18 — Angular Aria + CDK installed (2026-11-05)

`@angular/aria` for composite widgets (first: `AppMenu`), `@angular/cdk` for overlays.
Why: the admin shell's account menu is the first primitive that needs them (#5).

## #19 — API base URL from `environment.ts` (2026-11-05)

`environment.apiBaseUrl` → `API_BASE_URL` token; supersedes the hard-coded relative `/api` paths of #8 (the value is still `/api`).
Why: one place to point the app at another API (staging, a direct URL) without touching features.

## #20 — `ApiClient` + one API class per resource (2026-11-05)

Reads as `httpResource` signals through `ApiClient.resource`, writes as Observables failing with `ApiError`; features never use `HttpClient` directly. `VenuesApi` is the template.
Why: same shape for every feature, base URL and error mapping in one place, and signal reads that reload on their own.

## #21 — "Receipt" design system as tokens, patterns and primitives (2026-11-05)

The Claude Design export "Receipt" is the source: its values live in `tokens.css` as `--color-*` (via `light-dark()`), `--type-*`, `--space-*`, `--radius-*` and size tokens; its `r-*` classes become patterns without the prefix and with `data-*` variants (`r-badge--success` → `.badge[data-tone='success']`); behavior pieces are primitives. Tenant accent presets are `[data-tenant='<key>']` in `tokens.css`; font presets are left out until a venue can pick one.
Why: keeps the design's names recognizable while following `docs/ui.md` (semantic tokens, `data-*` variants, behavior only in primitives).

## #22 — Lucide icons via `@lucide/angular` (2026-11-05)

Nikola asked for Lucide. `@lucide/angular` (standalone, signal-based; the older `lucide-angular` stops at Angular 21), one component per icon (`<svg lucideLogOut>`), defaults `strokeWidth: 1.5, size: 18` in `app.config.ts` as the design asks.
Why: the design calls for one 1.5px line icon set; Lucide is the requested one. Cost: each icon component carries a compiled template (~4 kB raw, ~1 kB gzipped), and the package is one module, so every icon used anywhere lands in the initial bundle (the shell uses them). The initial-bundle warning budget is raised from 500 kB to 600 kB for this; if it nears that, replace the per-icon components with one data-driven icon primitive.

## #23 — Onest + JetBrains Mono from Google Fonts (2026-11-05)

Loaded with a `<link>` in `index.html` (`display=swap`), no font package.
Why: the design's fonts, both with Serbian Latin diacritics and Cyrillic; no dependency. Self-host if privacy or offline use requires it.

## #24 — Seeded Bauhaus pattern replaces block strips (2026-11-05)

The designer's handoff (`design-system/receipt/`, kept unchanged as reference) makes the brand signature a pattern generated from a seed. `generatePattern` is ported to TS in `shared/ui/pattern/` (FNV-1a over UTF-16 code units + mulberry32; call order and weights unchanged, snapshot-tested against the original JS) and drawn by `AppPattern`. Colors are `--color-brand-*` instead of the handoff's `--brand-*`, and classes follow #21 (`.pattern`, `data-kind`, `data-rot`, `data-fluid`). `.blocks` is removed.
Why: the same venue must look the same on web, POS, print and native, so nothing is stored or drawn by hand; the seed is always app data.

## #25 — Menu editor on CDK drag-drop and CDK Dialog (2026-11-05)

Categories and items are reordered with `@angular/cdk/drag-drop` (handle button per row, keyboard-free for now), edits open in CDK dialogs (`CategoryDialog`, `ItemDialog`, shared `ConfirmDialog`). Order is saved with one `PUT …/order {ids}` per drop, after an optimistic local move.
Why: stays in the Angular ecosystem (no extra libs), and one request per drop matches the backend's order endpoints.

## #26 — Patch `sr-Latn` plural rules at startup (2026-11-06)

Angular's `@angular/common/locales/sr-Latn` returns "other" for every number, so ICU plurals would read "4 stavki". `registerSerbianLatinPlurals()` re-registers `sr-Latn` with the `sr` plural function (CLDR shares the rules between scripts) before bootstrap.
Why: keeps plurals in ICU messages (the Angular way) instead of hand-rolled count helpers; one place to drop when Angular fixes the data.

## #27 — Menu themes: three templates, preset keys, one shared view (2026-11-06)

A menu has one theme (`menu_themes`, 1:1 with `menus`): template `racun` (one column receipt), `galerija` (photo cards) or `tabla` (dense board, size columns, dark by default), an accent from the ten `[data-tenant]` presets, a font from `[data-font]` presets (Onest, Manrope, IBM Plex Sans; the extra two load from Google Fonts only when used), light/dark/auto, and switches for photos, descriptions and the Bauhaus band. The themed menu is `PublicMenuView` in `core/public-menu/`, used by the guest page and by the editor's live preview (`/meniji/:id/dizajn`), so the preview is the real thing. Guest-side extras live in the same view: diacritic-free search, diet and "without allergen" filters, item sheet (CDK Dialog at the bottom), combos with savings, guest light/dark switch. Tags and allergens stay free text in the API; `core/menus/menu-labels.ts` is the shared vocabulary (14 EU allergens, diet tags, highlight tags) that the item dialog offers and the guest menu translates and filters by.
Why: keys instead of colors and fonts keep every combination readable (the design's tenant rules); one view avoids a preview that drifts from what guests see; a vocabulary on top of free text keeps OCR and old data working.

## #28 — Aria for every composite control (2026-11-06)

Audit after #11 and #12: `AppMenu` (menu) and `AppSegmented` (listbox) were already on `@angular/aria`; native `<select>` was not used, the venue currency was a free text input, row actions were loose buttons, and tag/allergen/filter chips were `aria-pressed` buttons. Now: `AppChipGroup` is a multi-select Aria listbox (tags and allergens in the item dialog, diet and allergen filters in the public menu); `AppSelect` is an Aria combobox (non-input host = select-only) with a listbox popup in a CDK overlay, `selectionMode="explicit"` so arrows move and Enter or click picks; row actions are Aria toolbars (`ngToolbar` / `ngToolbarWidget`); drag handles also move with Alt+ArrowUp/Down (CDK drag-drop has no keyboard reorder). Not Aria on purpose: dialogs (CDK Dialog), the switch (native checkbox with `role=switch`), native radio groups in menu design (already arrow-key groups), single on/off toggles (`aria-pressed` buttons) and public menu category chips (navigation links with `aria-current`, not tabs).
Why: Nikola wants Aria wherever it fits; it brings roving focus, typeahead and correct ARIA without our own key handling.

## #29 — MVP admin screens: QR, bulk prices, combos, photo import (2026-11-06)

On the backend contracts of #10 and #13. **QR**: the venue Ticket shows the code of `/public-link` (SVG preview loaded as a blob, since the request needs auth) with PNG (1024 px) and SVG download; SVG is the one to print. **Bulk prices**: a dialog in the menu editor (whole menu or one category, percent or amount, rounding that defaults to 10 RSD) with a client-side preview that copies the server's `adjustPrice` rule. **Combos** (`/objekti/:id/kombo`): list with status, savings, on/off switch and reorder; the editor builds slots from items of all the venue's menus (active menu first) with `AppSearchPicker`, an editable Aria combobox that filters without diacritics; regular price and savings are computed live like the server (cheapest option of a choice). **Photo import** (`/objekti/:id/uvoz`, `/uvoz/:importId`): camera button (`capture="environment"`, one photo per tap, appends) plus multi-file pick and drop, thumbnails in reading order (drag or arrow buttons), client-side checks for type, 15 MB and 20 pages; the review page polls every 2 s while anything is read, shows per-page status, photo quality and issues with our own text per `error_code`, and offers retake, retry, delete and add pages. Ready drafts are reviewed per page in Aria tabs: the original photo next to the items read from it (`page_index`), uncertain items highlighted with an "OK" to clear them, missing prices and names marked red; edits are saved before any page action and before commit, which is blocked until nothing is missing.
Why: these were the MVP gaps from the review; per-page tabs keep the comparison to one photo at a time, and saving before page actions keeps the user's corrections (the server appends a retaken page's result to an edited draft).

## #30 — Images, view stats, team, password reset, platform admin (2026-11-06)

Web side of the rest of #13. **Images**: `AppImageField` (in `core/media/`, since it calls the API) uploads to `/v1/media/images` with a purpose and stores the returned public URL; it replaces the URL text inputs for item and combo photos and the theme logo and cover. Only JPEG/PNG/WebP is offered, so iPhone Safari converts HEIC. **Views**: the guest page posts one view per tab session (`sessionStorage` guard, so refresh and language switch don't count); the dashboard shows 30 days of opens per venue as one-series bars with a hover tooltip and a hidden table. **Team** (`/tim`, owner and manager): members with role select and remove for the owner, invitations by email (managers invite staff only), revoke. **Links from emails** keep the backend's English paths: `/invite?token=` (existing account signs in and comes back; new person picks a name and password; the session switches to the inviting business) and `/reset-password?token=` (drops the local session after success, since the server revoked every token). `/zaboravljena-lozinka` asks for the link. **Platform admin** (`/admin`, nav entry and guard on `user.is_platform_admin` from `/v1/me`): businesses with usage, suspend/reactivate with a confirm, import limit per venue, OCR spend per business and model for 7/30/90 days.
Why: closes the MVP list; links keep the paths the backend already mails; admin is gated in the UI and checked again by the API on every request.

## #31 — Preload every page, shared venue list, list filters, venue cards (2026-11-06)

Nikola found each page slow the first time and asked for preloading, filters "almost everywhere", cards for few venues and a table for many, and no venue picking when there is only one. **Preloading:** `withPreloading(AppPreloading)` loads every lazy route after the first navigation; a tenant subdomain preloads nothing (guests only need the public menu), and the public menu and `/design` are opted out on the app host. **Data:** `VenuesStore` keeps one venue list per tenant (dashboard, venue list, venue page, guard), refreshed in the background on each visit, so pages render from cache. `ApiRequest.key` refetches a same-URL resource on tenant switch; `/v1/me` uses it (it used to stay on the old tenant after switching). **Filters:** `AppSearch` (search box, filters as you type, Esc clears) plus `AppSegmented` for status, in a `.filters` bar, all client-side with `matchesQuery` (diacritic-free, `shared/text/fold.ts`, also used by the public menu and `AppSearchPicker`): venues, venue menus (status), menu items (availability), combos (status), team (role), admin businesses (status, on top of the server search). While a reorderable list is filtered, drag and Alt+arrow moves are off. **Venues:** up to 8 venues open as Ticket cards (pattern seeded by name, whole card is the link), more as the table; the Kartice/Lista pick is remembered in `localStorage` (`menuly.venues.view`). **Layout:** admin pages use the full width (no `--content-max-width` on `main`); forms keep 48rem; admin Tickets drop the punch hole and are a light subtree (`data-theme="light"`) so their controls stay readable in the dark theme; the QR block is centered. **One venue:** `singleVenueGuard` on `/objekti` opens it directly; its page drops the back link and offers "Dodaj objekat" to owners there; the dashboard says "Otvori objekat".
Why: preloading removes the chunk wait on first visits; the shared list removes the repeated venue request; client-side filters cover the list sizes a business has without new API parameters.

## #32 — Theme and account in a collapsible sidebar (2026-11-06)

Nikola asked to move the theme switch and account menu from the top bar into the sidebar and to add a sidebar toggle. The top bar stays for page tools (for now only the sidebar toggle); the sidebar footer holds the theme button (icon + current theme) and the account menu (`AppMenu` with `icon`, `look="nav"`, `above`, and `compact` for icon-only), lined up with the nav items on one left edge; the business row has the top bar's height and bottom line. The panel button in the top bar collapses the sidebar to icons (`--sidebar-collapsed-width`, names stay as accessible names and tooltips), remembered in `localStorage` (`menuly.sidebar`). On phones (720px and below) the sidebar stays the horizontal bar and the top bar is hidden.
Why: Nikola wants the top bar for other page tools later; a collapsed sidebar gives wide tables more room.

Template `etiketa`, inspired by "micrographics" spec-label design (screenshots in project files `inspiracija/micrographics/`), our own take and not a copy: every item is a label card with a code `№ 02.05` (category and item position in the menu as saved, so search and filters never renumber what a guest may quote to staff), a decorative barcode, a big name, and the price under a dashed rule. Each category gets one of four print stripes (`--color-stripe-1..4`: coral, steel blue, mustard, bone/grey), cycled by category order, on the card's top edge (prints in once; reduced motion starts it full) and as a striped mark in the header. Combos without a photo become a notched ticket with two overlapping circles whose shared part is striped: two items, one combo. The accent preset still drives the ticket and badges. ## #34 — "Racun" becomes a paper strip with a stamp (2026-11-09)

The default template now looks printed: the menu sits on a paper strip (`--color-surface` with `--texture-grain`, an inline SVG noise) over a darker table (`--color-receipt-backdrop`), with zigzag torn edges top and bottom (CSS mask, `--size-receipt-zigzag`). It is signed at the end with a rotated rubber stamp in the accent color: the venue name and "MENI" around the ring, the name's first letter and the year inside (SVG `textPath`, unique id per view for the editor preview). Host and sticky-bar backgrounds live in the component CSS because component styles are unlayered and beat `@layer patterns`.
Why: second step from the micrographics inspiration (#33); the receipt is our default and Receipt is the design system's name, so it should feel like one.

## #35 — Menus choose their own languages (2026-11-09)

A menu offers Serbian (the base, always there) plus any languages the owner adds in the editor's "Jezici" dialog (`menus.languages`, `{ code, name }`, max 10; quick picks or a custom code like `pt-br`). Category, item, size and combo forms get a language tab per menu language (`LanguageTabs`, `core/menus/`); empty translations fall back to Serbian. Removing a language keeps its text, so adding it back restores it. Guests see no picker with one language, a one-tap pill to the other with two, and a native `<select>` over the pill with more. The app's own texts stay sr/en: Serbian is the root build, English `/en/`, and any other menu language opens the English build with `?lang=xx` (the public menu page reads it as an input).
Why: Nikola wants owners to add any language and type its translations themselves, with no picker when there is nothing to pick.

## #36 — Fifth template "plakat" and a second header band "trake" (2026-11-09)

From Swiss/Bauhaus poster inspiration (project files `inspiracija/posteri/`), our own take: `plakat` puts the menu on cream poster paper (`--color-poster-paper`) with category heads as black capsules (one sharp corner) holding a numbered paper circle, bold names, one dot of the accent color before items tagged as a highlight (novo, preporuka, specijalitet kuće), combos as black rounded blocks, and a red/yellow/blue ribbon above the footer. Shapes use `--color-text`/`--color-text-inverse`, so dark mode inverts them. The header band now has a choice (`menu_themes.pattern`, migration 00013): `bauhaus` (the existing shapes) or `trake`, a seeded grid of narrow brand-color bars (`AppStripes`, `generateStripes`) that never repeats a color above itself.
Why: Nikola picked the poster ideas that keep a menu readable; op-art and gradient posters were left out (readability, flat system).

## #37 — Menuly mark: a lowercase "m" of two arches (2026-11-09)

The platform mark is a lowercase "m" drawn as two thick arches, `brand-amber` then `brand-periwinkle`, on a `brand-ink` rounded square (`public/favicon.svg` is the source, 64×64 grid). From it come `favicon.ico` (16/32/48), `apple-touch-icon.png` (180, full-bleed square), `icon-192.png`, `icon-512.png` and `icon-maskable-512.png` (mark inside the 80% safe zone) for `manifest.webmanifest`. PNGs were rendered from the SVG with Chromium and the ICO packed with ImageMagick; regenerate them the same way when the mark changes.
Why: there was no logo, only Angular's default favicon. A 2×2 Bauhaus tile would look like a venue mark in the sidebar, and a receipt drawing loses its detail at 16 px; the "m" stays readable at 16 px and is clearly the platform, not a venue.

## #38 — "Mozaik": a living glyph-tile band and a mosaic combo card (2026-11-10)

From a screen recording Nikola found (project files `inspiracija/novi-dizajn/`), our own take: a third header band `pattern: mozaik` (migration 00014). `AppMosaic` draws glyph tiles (square, ringed square, cross, diamond, dash, lone dot) on a canvas from seeded 3D value noise whose third axis is time, so the field flows instead of blinking: dense in the top-left, breaking up toward the bottom-right, 10 steps a second. It is still with reduced motion and stops off screen or in a background tab. Colors are `--color-mosaic-1..5` on `--color-mosaic-ground`, the same in both themes, read by the canvas once. With `mozaik`, the featured combo becomes a dark card with its own mosaic, a "Kombo" pill and a large light title, in every template.
Why: Nikola wanted the looping "wow" motion of the original; canvas keeps ~400 changing tiles cheap, and the guest's reduced-motion setting still wins.

## #39 — Geometric category illustrations (2026-11-11)

From poster inspiration (project files `inspiracija/posteri-2/`, the geometric ice cream), our own take: with `show_illustrations` (migration 00015, off by default, on in the demo) every category head gets a small drawing built only from circles, half circles and capsules (`AppCategoryArt`): cup, cone, beer, wine, cocktail, juice, pan, cake, pizza, burger, salad, fish, bowl, plate. `artKindFor` picks it from the category name (folded, sr + en keywords, first match wins, plate otherwise); "pić" is read before folding so drinks never become pizza. Colors are the venue accent plus brand amber/periwinkle/pink/teal; on the black "plakat" capsule the drawing sits on a paper disc. Steam and bubbles loop gently and stop with reduced motion.
Why: most menus have no photos; a drawing per category gives them the same character without any upload, and the client picks it, so the API stores only the switch.

## #40 — Guest menu in the initial bundle, boot mark in index.html (2026-11-11)

Measured on throttled 3G (Chrome's Slow 3G and Fast 3G, 4x CPU) the guest menu was blank for 19.8 s / 6.2 s: after the initial bundle came a chain of four lazy chunks (routes file, page, view, shared venue helpers), each one round trip, and only then the menu request. The tenant routes now sit inline in `app.routes.ts` and `PublicMenuPage` (with `PublicMenuView`) is imported eagerly, so the menu request starts right after the initial bundle: 11 s / 4.1 s. Admins pay about 22 kB gzipped more on their first load. `index.html` shows the Menuly mark until the app starts (`app-config.js` is `defer`, so it no longer holds up the first paint), and nginx gzips JS/CSS.

Why: guests open the menu from a QR code on mobile data; that path matters more than a slightly larger admin bundle.

## #41 — Guest pages render on the server (Angular SSR, hybrid) (2026-11-12)

Crawlers, link previews (WhatsApp, Viber, Facebook) and AI crawlers mostly don't run JavaScript, so every guest URL looked like the same empty shell. Now `@angular/ssr` with `outputMode: "server"` renders only tenant-subdomain pages on the server (`app.routes.server.ts`: app-host paths `RenderMode.Client`, the rest `RenderMode.Server`), with incremental hydration and event replay; admin and sign-in stay a client-side SPA. Production has two images from one build: `menuly-web-ssr` (Node, `src/server.ts` on plain `node:http`, no Express since nginx serves the static files) and `menuly-web` (nginx), which sends tenant-subdomain pages to the SSR server and keeps them 60 s in `proxy_cache`. On the server the API is called directly (`API_INTERNAL_URL`, swapped in at the `HttpBackend`, after the transfer cache, so the browser reuses the response instead of fetching it again). A missing menu answers 404 and a failed API 503 via `RESPONSE_INIT`; menu opens are counted only in the browser. New dependencies: `@angular/ssr`, `@angular/platform-server`. Plan and next steps (meta, JSON-LD, sitemap, agents): project doc "Menuly: SEO i agentska optimizacija".
Why: SEO and agent discovery need the menu in the HTML; SSR keeps one codebase and stays inside Angular, and limiting it to guest pages leaves the admin unchanged.

## #42 — Guest menu head and JSON-LD come from the menu itself (2026-11-13)

`MenuSeo` (`core/public-menu/menu-seo.ts`) writes a guest page's head from the same `PublicMenu` the page shows: title (`{venue} · meni i cene`), a description built from the category names, canonical, one `hreflang` per menu language plus `x-default` (Serbian), Open Graph, and one JSON-LD graph: `FoodEstablishment` (address, phone, opening hours) → `Menu` → `MenuSection` → `MenuItem` → `Offer` per variant (price, currency, in/out of stock), combos as their own section. The canonical follows the language actually served, so `/en/{venue}` of a Serbian-only menu points at `/{venue}`. Diet tags map to `suitableForDiet`; schema.org has no allergen property for a menu item, so allergens are a sentence in its description. A missing menu and the seeded `demo` tenant get `noindex`. Owners enter nothing extra; `FoodEstablishment` becomes a precise type (restaurant, café, bar) and the address structured once venues have those fields.
Why: search engines, link previews and AI agents read the head and the JSON-LD, and deriving both from the menu means they can never drift from what guests see.

## #43 — Venues say what and where they are, for local search (2026-11-13)

A venue gets optional fields the owner fills in under "Vidljivost u pretrazi" and next to the address: type (restaurant, café, bar, fast food, bakery, pastry shop, other), city, postal code, country, coordinates, up to 5 cuisines and a short description (migration 00017). The form takes coordinates as one text field in the form Google Maps copies ("44.8176, 20.4569") and cuisines as a comma-separated list; the API stores two numbers (both or neither) and a text array. `MenuSeo` uses them: the JSON-LD type follows the venue type (`Restaurant`, `CafeOrCoffeeShop`, `BarOrPub`, `FastFoodRestaurant`, `Bakery`, else `FoodEstablishment`), the address is a `PostalAddress`, plus `geo`, `servesCuisine` and `description` (Serbian page only, since owners write it in Serbian), and the city joins the title (`{venue}, {city} · meni i cene`) and the description.
Why: "kafana Beograd" style searches and agents asking for a place nearby match on type, city and coordinates, which a free-text address cannot give them; all fields stay optional so existing venues keep working.

## #44 — Each tenant subdomain has its own robots.txt, sitemap.xml and root page (2026-11-13)

`GET /v1/public/tenants/{tenantSlug}` lists a tenant's venues with a published menu. The SSR server (`src/server.ts`) answers three things from it before Angular: `/robots.txt` (allow all, names the sitemap), `/sitemap.xml` (every menu in each of its languages with `xhtml:link` alternates and `lastmod`; empty for the `demo` tenant, whose pages are `noindex`) and the root, which redirects (302) to the menu when the tenant has one venue. With several venues the root is `TenantPage`, a client-rendered list of them (`noindex, follow`). The URLs come from the same `menuUrl` as the page's canonical and hreflang links.
Why: every tenant is its own site to a search engine, so each needs its own sitemap; building it in the SSR server keeps one URL rule and needs no nginx or backend knowledge of how languages map to paths. The root used to be a "not found" page, which is what a guest typing the bare address saw.

## #45 — Fonts are self-hosted (2026-11-13)

Replaces #23 and the font part of #27. Onest, JetBrains Mono, Manrope and IBM Plex Sans are variable `woff2` files in `public/fonts` (latin, latin-ext, cyrillic; all four are SIL OFL), with their `@font-face` rules inline in `index.html` (`font-display: swap`, `unicode-range`, so a page downloads only the scripts it shows). No request goes to Google any more, and a menu's theme font is known to the server-rendered page instead of being added by JavaScript after it starts. The files are served with a one-year immutable cache, so a new font version gets a new file name. Guest photos also carry the item or combo name as `alt`, decode off the main thread, and the cover is fetched with high priority.
Why: a guest on 3G paid for a second connection (DNS, TLS) before any text got its font, the theme font flashed in late, and loading fonts from Google sends every guest's IP to a third party, which EU courts have ruled against.

## #46 — Menus for AI agents: Markdown, JSON and llms.txt (2026-11-13)

Every guest menu is also served as one Markdown document at `/{venue}.md` (`/en/{venue}.md`, `?lang=`), built in the SSR server from the same public API response as the page (`menuMarkdown`): venue, address, hours, sections, items with prices per variant, allergens, tags, availability and combos. The page's head links it and the API's JSON with `<link rel="alternate" type="text/markdown">` and `type="application/json"`, and each tenant subdomain has an `llms.txt` (llmstxt.org) listing its menus in both forms. Markdown answers carry `X-Robots-Tag: noindex`. Labels are Serbian for a Serbian menu and English otherwise, from a small table in the file, because `server.ts` runs before `$localize`; allergen and diet tags stay as stored (Serbian).
Why: an agent answering "what does this place serve and what does it cost" reads a small Markdown file far more reliably and cheaply than a themed HTML page, and `llms.txt` plus the alternate links are how it finds that file.
